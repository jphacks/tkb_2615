# アーキテクチャ

## コンポーネントの流れ

~~~text
CLI / ローカルHTTPサーバー
        |
Project、Scenario、Inspector、Demoサービス
        |
Scenario + Policy設定 -> WorldState -> 決定的tick engine
        |                            |                |
地域・Provider adapter             |             EventQueue
任意LLM adapter                    |             EventLog
        |                            |
ProjectStore / TimelineStore <- Checkpoint / BranchRuntime
        |
Run成果物、履歴index、Inspector projection、比較レポート
~~~

Python標準ライブラリのHTTPサーバーがローカルブラウザーアプリを配信します。ブラウザーは型付きrequestを送信し、simulation stateを直接書き換えません。保存済みRunのInspectorはread-onlyです。Project操作は別の検証済みcommandを使います。

## モジュールの責務

| 領域 | 主な責務 |
|---|---|
| core | WorldState、simulation clock、keyed RNG、tick engine、Checkpoint |
| domain | 人物、施設、Zone、route、資源、職員、運営規則 |
| events | 予定・実行済みevent、型付きhandler、EffectProgram |
| policies | 行動、ニーズ、空間、心理、社会、情報モデル |
| experiments | Scenario、Run、Branch、timeline、metrics、evaluation |
| inspection | 証拠検索、Run projection、trace要約 |
| region | 地域データ、geometry検証、施設図面取込 |
| llm | Provider adapter、型付き出力、cache、応答再生、利用額記録 |
| storage | Project、asset、Run、Checkpoint、履歴indexの永続化 |
| web | ローカルHTTP route、Project API、Inspector、Demo、ブラウザーasset |

実装の正本はパッケージ構成です。公開入力・状態契約はsrc/sheltersim/contracts、event/world model、およびserializationと互換性を確認するテストにあります。

## シミュレーションと状態境界

- 時刻は整数分です。event順と同順位の決着は、固定IDと明示的なsort keyで決めます。
- WorldStateが変更可能なsimulation stateの正本です。Policyとadapterは型付き提案を作り、controllerが検証して適用します。
- controller（`experiments/runner.py`の`OfflineSimulationController`）がtickの入口です。各段階の処理は`experiments/phases/`の`dispatch`、`update`、`propose`、`arbitrate`、`sample`、`metrics`に1モジュールずつあり、controllerが継承します。`_run_*_phase`がその段階の手順の並びで、手順は名前付きのメソッドなので、1つの手順だけを別の実装（Rustなど）に差し替えられます。移動の経路と予定の処理（`_route`、`_schedule_travel`）は、他の段階からも呼びますが、主に使う`propose`にあります。
- dispatchの段階は、Rustがあれば`native/src/rules/dispatch.rs`のループが動きます。`social_interaction`と`agent_travel_complete`はRustの関数で、ほかのイベント、Rustの関数が断ったイベント、差し替えられたhandlerは、`EventDispatcher.dispatch_one`（イベント1件分のPythonのdispatcher）が処理します。イベントの順序、同順位の解決、`id_counters["event"]`は同じです。Rustの関数が処理したイベントの記録は、Pythonが読むときに`EventLogRecord`になります（[lanes/m3-dispatch.md](rust-port/lanes/m3-dispatch.md)）。
- Rustの接触のkernelは、社会の伝播が`native/src/rules/social_propagation.rs`、情報が`native/src/rules/information.rs`、共通の抽選が`native/src/contacts.rs`にあります。社会の伝播は更新の段階の手順`_social_propagation`そのものを置き換えます（`experiments/phases/segments.py`）。traceがあるとき、`CounterRNG`でない乱数、方策の派生クラスはPythonの手順が動きます。情報は標本の段階の手順`_sample_information_contacts`を同じように置き換えます。
- Rustの拡張があるとき、世界はRustの状態を`world.__dict__["_core"]`（`WorldCore`）に持ちます。世界の中身と一緒に動くので、`world.__dict__.clear()`・`update()`の差し替えはそのままです。`SHELTERSIM_NATIVE=0`では持ちません。Rustが持つのは`psychological_distress_v1`、`social_propagation_v1`、`information_spread_v1`、`staff_dynamics_v1`、`agent_dynamics_v1`、`movement_v1`（規則はまだPythonです）、`body_state_v1`（`record_social_event`と毎tickの書き込みはRustです。ハンドラーと人口の規則はPythonのまま1項目ずつ転送します）、`staff_operations_v1`、`shared_operations_v1`と`metric_state`です（`core/state_mirror.py`の`OWNED_NAMESPACES`・`OWNED_FIELDS`）。持っている項目は`TrackedDict`・`TrackedList`の木になり、`model_state`自体は`NamespaceTable`になって、Pythonからの書き込みはRustの行へ、Rustからの書き込みは木へ届きます。行に合わない値が書かれると行を捨て（taint）、kernelは`Unsupported`を返し、Pythonの規則が木の上で動くので、エラーは変わりません。kernelが素の入れ物と同じように読むのは、この追跡する型だけです（`native/src/core/tracked.rs`）。ほかの派生型はPythonの処理に任せます。名前空間の検証をRustに任せる登録（`register_rust_validator`）と、段階の手順をRustに差し替える登録（`experiments/phases/segments.py`）、ほかのモジュールが関数として呼ぶ規則をRustに任せる印（`core/kernels.py`の`kernel_first`）があり、移植の作業は`core/world.py`を編集しません。手順は`docs/rust-port/lanes/p5-template-namespace.md`と`docs/rust-port/lanes/p4-world-core.md`にあります。
- Rustの拡張があるとき、`world.agents`、`facilities`、`staff`、`support_requests`、`active_tasks`は`IdMap`（`core/state_mirror.py`。dictの派生型で、読み取りはdictのまま）です。入っている実体（`AgentState`、`NeedState`、`FacilityState`、`StaffState`、`SupportRequestState`、`ActiveTask`）はPythonのdataclassのままで、属性の読み取りは今までどおりインスタンスから読みます。同じ値を`native/src/state/entities.rs`の型付きの行が持ちます。属性への書き込み（`__setattr__`）、`IdMap`への出し入れ、IDのリスト（`TrackedList`）への書き込みが行に届きます。`world.support_requests = {...}`のように丸ごと代入すると`WorldState.__setattr__`が受けます。行に合わない値が書かれると、値はPythonのオブジェクトにそのまま残り、ストア全体をtaintして、Rustの規則は`Unsupported`を返します。`SHELTERSIM_NATIVE=0`では素のdictとdataclassです。設計の判断と計測は`docs/rust-port/lanes/p6-entity-windows.md`にあります。
- Rustの拡張があるとき、更新の段階の心理の3つの手順（`_psychology_update`、`_update_long_term_psychology`、`_apply_state_deltas`）は`native/src/rules/psychology.rs`のkernelが行います。人の行を読み、行にない値（区域の環境、体調の記録、情報）は`native/src/rules/world_view.rs`の写しから読みます。心理のtraceを記録するtickの`_psychology_update`と、kernelが知らないPolicy（クラスの完全一致で判断します）はPythonの規則が動きます。結果は同じで、`policies/psychology.py`は比較の基準として残ります。記録は`docs/rust-port/lanes/a-psychology.md`にあります。
- Rustの拡張があるとき、段階が作る`WorldView`（`_view_after_movement`、`_view_for_proposals`）は`native/src/rules/world_view.rs`が行と名前空間から作ります。中身はRustの値の写しで、`agents`などのPythonのオブジェクトは、Pythonの読み手が最初に求めたときに作ります（`WorldView.__getattr__`）。値は`from_world`・`after_state_update`とビットまで同じで、監査のハッシュも同じです。扱えない値は`Unsupported`になり、`from_world`が動きます。記録は`docs/rust-port/lanes/g-world-view.md`にあります。
- Rustの拡張があるとき、提案の段階の`_propose_due`と`_observed_state`の計算は`native/src/rules/behavior.rs`のkernelが行います。`WorldView`のRustの写しを読むので、Pythonの`agents`は作りません。作る`ActionProposal`と記録用のdictは、`policies/behavior.py`の結果とビットまで同じです。Policy・runner・乱数がクラスの完全一致で組み込みのものでないとき、Pythonが作った`WorldView`、Pythonの規則がエラーにする値は、`Unsupported`になってPythonの規則が動きます。`policies/behavior.py`は比較の基準として残ります。記録は`docs/rust-port/lanes/h-behavior.md`にあります。
- Rustの拡張があるとき、`_propose_due`と`_observed_state`は`native/src/rules/decisions.rs`の行（`ProposalRow`、`ObservedRow`）を返します。`_apply_effect`のPythonの本体が読む項目は行が答え、それ以外を読むと`ActionProposal`を作ります。`_record_outcome`（`record_decision`、行動の周期、判断の記憶の順）も同じkernelが行います。`_IndexedMetricSink.observations`には、判断の行がJSONのbytesとして入り、`HistoryIndex.ingest`が読みます。traceのあるRunなど、`decision_sink`を宣言していない、または何かを書くsinkでは、この手順はPythonで動き、文書は変わりません。
- Rustの拡張があるとき、`social_network_v1`はRustの行（`native/src/state/social_network.rs`）が持ち、イベントの記録（`observe_event`）、社会の状態の文脈、社会的な行動のハンドラーの成立する枝は`native/src/rules/social_network.rs`、`social_dialogue.rs`、`social_interaction.rs`で動きます。それ以外の枝とエラーの文はPythonの規則です。
- Rustの拡張があるとき、`resource_ledger_v1`はRustの行（`native/src/state/resource_ledger.rs`）が持ち、監査の記録は項目ごとの正準bytesです。在庫の操作、KPIの列、毎分の検証、使った予約IDの確認は`native/src/rules/resources.rs`で動き、名前空間をその場で書きます。保存の前の監査の再生、エラーの文、`domain/care_receipts.py`はPythonのままです（[lanes/m4-resources.md](rust-port/lanes/m4-resources.md)）。
- Rustの拡張があるとき、`resource_service_v1`はRustの行（`native/src/state/resource_service.rs`）が持ち、水と食事の提供の`arbitrate`の1回分、`complete`、`request`は`native/src/rules/service.rs`で動きます。`_apply_proposal`は`_apply_effect`（世界に何をするか）と`_record_outcome`に分かれ、`_apply_effect`のうち職員の窓口に行かない行動は`native/src/rules/proposals.rs`、`_route`と`_schedule_travel`は`native/src/rules/travel.rs`が動かします。独立したFIFO、`cancel`と`interrupt_for_staff`、`seek_help`と`seek_information`、仮設の部屋のベッド、辺の容量のある経路、エラーの文はPythonの規則です（[lanes/m4-service.md](rust-port/lanes/m4-service.md)）。
- Rustの拡張があるとき、`movement_v1`はRustの行（`native/src/state/movement.rs`）が持ち、毎 tick の移動の規則（`advance_movement`、`start_movement`、`finish_movement`、経路の計画）は`native/src/rules/movement.rs`が動かします。間取りはPythonが検証したモデルから`rules/movement_geometry.rs`がデータとして読み、解析済みの設定の同一性と、上書きの移動・仕切りのバイト列が変わるまで使い回します。列の旅の引き直しと、歩く途中で列の枠に置く人がいる tick は順序に依存するので、その tick は全部Pythonの規則が動かします。詳しくは[docs/rust-port/lanes/m4-movement.md](rust-port/lanes/m4-movement.md)にあります。
- Rustの拡張があるとき、設備の列の毎 tick の規則（`prepare_facility_queue`、`progress_physical_queue_positions`、`progress_physical_queue_head_to_service`）は`native/src/rules/queues.rs`が動かします。列の旅のイベントもここで予定します。列を離れる人がいる呼び出しと、独立したFIFO（`facility_queues_v1`）はPythonの規則が動かします。`facility_queues_v1`の状態はPythonのdictのままです。詳しくは[docs/rust-port/lanes/m4-queues.md](rust-port/lanes/m4-queues.md)にあります。
- Rustの拡張があるとき、`staff_operations_v1`と`shared_operations_v1`はRustの行（`native/src/state/staff_operations.rs`、`shared_operations.rs`）が持ちます。職員が何も始めない tick の規則（`StaffService.assign_pending`、`update_staff_operations`、`assign_staff_operations`、`schedule_staff_operation_relief`、指標の支援待ちの読み取り）と、ケアの受領記録の追記、tick の検証は`native/src/rules/staff.rs`、`common_operations.rs`が動かします。職員が依頼や作業を取る tick は、経路とイベントが要るので、その手順を全部Pythonの規則が動かします。作業のイベントの規則もPythonのままで、1項目ずつ転送します。詳しくは[docs/rust-port/lanes/m4-staff.md](rust-port/lanes/m4-staff.md)にあります。
- Rustの拡張があるとき、`effect_program_v1`はRustの行（`native/src/state/effect_program.rs`）が持ち、EffectProgramのイベントのガード、5つのハンドラー（設備、環境、一時空間、床図、構造）、変更の重なりの読み取り、`validate_effect_program_state`は`native/src/rules/effects.rs`で動きます。ハンドラーは世界を写して変更し、検証して差し替える流れをそのまま使います。パラメーターのpydanticの契約、`validate_effect_program`、`schedule_effect_program`はPythonのままで、成功以外（抑止と失敗）は世界を変えずに`Unsupported`を返し、Pythonの規則が同じ文を出します（[lanes/m6-effects.md](rust-port/lanes/m6-effects.md)）。
- Rustの拡張があるとき、毎分のKPIの列（`MetricSnapshot.from_world`、`operational_kpi_values`）は`native/src/rules/metrics.rs`が行から読みます。毎分の検証のうち、実体と予定イベントの規則は`native/src/rules/tick_validation.rs`の`entity_rules`が1回の呼び出しで確かめます。行ではなくオブジェクトを読み、文を持ちません。すべて通るときだけ返し、それ以外は`Unsupported`で、`WorldState._validate_entity_rules`と`_validate_event_rules`のPythonの規則が動いて同じ文を出します。Checkpointの保存の前の完全検証はPythonの規則を読みます（[lanes/m5-metrics.md](rust-port/lanes/m5-metrics.md)）。
- 乱数はScenario seedと安定したdomain IDから決定します。simulation結果の判断にwall-clockやmodule-global乱数を使いません。
- EventQueueは今後処理する予定を、EventLogは結果を記録します。sourceやcausationを含む、相互に区別された記録です。
- TickEngineは毎分の終わりに、現在の状態と、その分に追記された履歴記録（直前の1件を含む）を検証します。追記専用の履歴（共有運用、生活状態の社会履歴、給水・配食の依頼と停止の履歴、資源台帳の監査記録）とEventLogの全体の再生、共有運用の支援ライフサイクルの再構成は、Runの開始・終了とCheckpointの作成・復元で行う完全検証で確認します。毎分の検証が履歴全体を再走査しないため、1分あたりの検証時間は履歴の長さに比例して増えません。Rustの拡張があるとき、TickEngineの毎分の検証（`WorldState.validate_after_tick`）は、前の分の検証から変わっていないと示せるものをさらに省きます（`core/tick_validation.py`）。根拠は次のとおりです。規則そのものは減らしていません。省いたものは完全検証がすべて確かめ、検証に失敗した世界は覚えていたことを捨てます。(1) 設定の検証は、`model_configs`が前に通ったときの写しと等しい間は省きます。等しさの比較は`1`と`True`を区別しませんが、tickは`model_configs`を書かず、値は完全検証が確かめます。(2) 解決済み・未解決になった支援の依頼（`support_requests`）は、自分の項目、人のIDの集合、そして「今の分より後でない」という形でしか時刻に依存しません。`SupportRequestState`は項目への代入を知らせるので、代入された依頼と新しい依頼、まだ終わっていない依頼だけを確かめます。辞書の値が同じオブジェクトのままかも毎分確かめ、人のIDが変われば全部を確かめ直します。tickの途中で終わっていない依頼を探す走査（`WorldState.unsettled_support_requests`）も同じ記憶と知らせを使い、確かでないときは全部を読みます。(3) `population_presence_v1`、`population_lifecycle_v1`、`geometry_overlay_v1`は、正準JSONと、規則が読むほかの状態（人のID、区域のID、設備の区域）が変わらなければ省きます。時刻や他の状態と比べるもの（`archive_path`、保留の移動、仮設の部屋、経路の変更）があるときは省きません。(4) 共有運用は、最新の記録とそれ以外の項目が同じなら省き、新しい記録は従来どおり確かめます。(5) `used_reservation_ids`は追記専用なので、新しいIDだけを型と重複まで確かめ、それより前は通ったときのIDの列と比べます。(6) 社会関係・体調の関係の記録は、Rustの行が、書かれた記録を自分で控えます（転送も規則の書き込みも通ります）。毎分はそれだけを確かめ、人のIDが変われば全部を確かめ直します。行がtaintしたとき、`SHELTERSIM_NATIVE=0`のときは、Pythonの規則が毎分全部を読みます。大きな辞書の走査（人、社会関係・体調の関係、体調、行動の記憶、位置）は、すべて規則を満たすと分かったときだけ`true`を返すRustの確認を先に通します。それ以外（型が素でない値を含む）はPythonの規則が判定するので、受け入れる範囲とエラーは変わりません。Rustが持つ名前空間（`psychological_distress_v1`、`information_spread_v1`、`staff_dynamics_v1`）は、行を読むkernel（`register_rust_validator`）だけが規則の前に立ちます。行に入らない値はtaintに、入るが規則に合わない値はkernelの`false`になり、Pythonの規則が木を読んで同じエラーを出します。`rust_validated`は、世界がその行の木と、行が従う`IdMap`を今も持っていることも確かめるので、`world.__dict__["model_state"]`への代入や`dict.__setitem__(world.model_state, ...)`、`dict.pop(world.staff, ...)`もPythonの規則に届きます。実体の規則は、行を信じずオブジェクトを読みます。`agent.__dict__`への書き込みが行に届かないからです。追跡する木の節点への`dict.__setitem__`だけは行にもkernelにも届きません（`src/`にはありません。`test_tracked_write_lint.py`が見ます）。どの規則を何が証明するかは`docs/rust-port/lanes/t-tick-validation.md`にあります。Rustの拡張がないときは、毎分`validate(validate_event_history=False)`を実行します。完全検証のうちEventLogについては、次のように読む量を減らしています。EventLogは、記録を足すときに作る索引（IDと順序番号、イベントの種類ごと、来歴に介入（EffectProgram）の印を持つ記録）を持ちます。運営イベント・介入・環境・インフラの完全検証は、確かめるイベントの種類の記録だけを索引から読み、IDによる参照も、EventLogを写した辞書ではなく索引（`EventsById`）で引きます。ほかの種類の記録は、これらの確認を素通りするだけなので、確かめる範囲は変わりません。EventLog自体の監査（IDと順序番号の重複、実現時刻）は、前の監査で確かめた記録が先頭に同じオブジェクトのまま残っていれば、増えた記録だけを、それが索引の指す記録であることと合わせて確かめます。記録は凍結されていて、追記しかされないためです。先頭の記録が差し替わっていたり、前より早い時刻での監査だったりすれば、全体を確かめ直します。
- Checkpointの保存の前の完全検証（`world.validate()`）は、書き手の履歴キャッシュ（`CheckpointHistoryCache`）があるとき、追記専用の履歴の古い項目を読み直しません（`core/save_validation.py`）。読まないのは次の5つの履歴の、前の保存で通った項目だけで、他のものはすべて保存のたびに読みます。読まない根拠は次のとおりです。(1) 保存のたびに、各履歴の全項目が前の保存の文書のままかを確かめます。項目を文書と比べる比較（`sheltersim_native.same_json_items`）は`==`より厳しく、型まで見ます（`1`・`1.0`・`True`は別、タプルとリストも別、`0.0`と`-0.0`も別）。一度この比較を通った項目は、同じオブジェクトを同じ順で持ち続けていることで確かめ（`HistoryPins`。中のオブジェクトへの参照を持つので、同じアドレスに別の値が来ることはありません）、そう言えなければ文書と比べます。項目の変更・削除・差し替えがあれば、同じ保存でその履歴全体を読み直し、規則が今までどおり判定します。Runの終わりまで待つものはありません。(2) 古い項目の規則が読むほかの状態も比べ、違えば履歴全体を読み直します。`request_history`・`queue_stall_history`は既知の人のID・区域のID・設備の種類、`body_state_v1.history`は過去の人を含むID、`resource_ledger_v1.audit`は倉庫IDと既知の人のID、`shared_operations_v1.history`は保持中の職員の運営履歴（`staff_operations_v1.history`）の正準JSONです。(3) 時刻が戻るか`event_log`が別のオブジェクトになると、覚えていることをすべて捨てます。(4) 資源台帳の監査の再生と共有運用の支援ライフサイクルの再生は、前の保存の途中状態から続けます。先頭の項目が落ちた履歴（`history_truncated`）は再生の始点が変わるので、毎回全体を読みます。(5) 覚えたことは書き手のキャッシュが持ち、Rustの拡張があるときだけ使います。読み込み・分岐・再開の世界は新しいキャッシュで始まるので最初の検証は完全です。失敗したCheckpointの作成は覚えたことを捨てます。Runの開始・終了（`TickEngine.run`）、読み込み、`to_dict`などの完全検証は、これまでどおり全項目を読みます。
- 資源台帳への操作（納入、損失、予約、解放、消費）と毎分の指標集計は、現在の残高・予約と、直前の監査記録・各資源の最新の監査記録を確認します。Pythonの規則の操作は変更する口座だけを複製した候補に適用し、確認を通ってから差し替えます（Rustの規則は、確認を通ってからその場で書きます）。監査記録の全件の再生は完全検証で行います。
- Checkpointは対応する復元に必要なstateとruntime情報を含みます。BranchRuntimeは分離したstateを復元し、兄弟Branchで可変queue、RNG状態、actor objectを共有しません。
- 1 tick の中と tick の間で、次のものを作り直しません。結果を変えない根拠と入力の一覧は`docs/rust-port.md`のB4にあります。提案の段階の`WorldView`（`policies/world_view.py`。`policies/behavior.py`からも読めます）は更新の段階のものから作り、更新が書く項目だけを読み直します（`WorldView.after_state_update`）。解析した設備の形状、`selected_models`、部屋の中の経路、区域の環境は、コントローラーごとに持ちます（`ContextVar`のscopeか引数で渡すので、スレッドや分岐をまたぎません）。`model_configs`は分の最初に写しと値で比べ、違えば全部を捨てます。経路と環境は、読む`model_state`の項目を呼ぶたびに値で比べます。`EventQueue`は索引を持ちますが、`pending()`の順と保存の形は変わりません。Rustの拡張があるとき、`EventQueue`はRustが持ち（`native/src/state/events.rs`）、Rustの規則が予定したイベントの`ScheduledEvent`は、Pythonが読むときに作ります。行動の周期の記録（`agent_action_lifecycle`）はRustの規則がbyte列として追記し（`native/src/rules/action_lifecycle.rs`）、`EventLogRecord`はPythonが読むときに作ります。開いている行動はコントローラーの`ActiveActions`がRustの行で持ちます。保存はされず、復元のときにイベントログから作り直します。
- 計算を進めるworker（`TimelineStore`の継続計算）は、Checkpointを保存するたびに、前の保存で変換した追記専用の履歴（EventLog、KPIと資源の標本、上の追記専用の履歴）の文書と正準JSONのbyte列、EventLog記録の復元結果を再利用し、新しく増えた分だけを変換・復元します（`core/checkpoint_cache.py`、#44）。保存されるCheckpointのbyte列、hash、archiveのchunkは、全体を変換した場合と同じです。世界の文書の各フィールドの正準JSONは1回だけ作り、文書・hash・chunkで使い回します。Checkpoint v2のhashはchunkのhashの木なので（`docs/project-persistence.md`）、保存は新しいchunkだけをhashします。項目は同一性で照合し、古い項目を先頭から捨てる窓にも対応します。凍結されていない履歴の項目は保存済みの文書と等しい間だけ再利用し、書き換えられていれば変換し直します。保存前の完全検証は、従来どおり保存のたびに行います。復元の確認では、保存した文書から世界を復元し、それが直前に完全検証した世界と同じ状態か（`WorldState.same_state`）を比べます。同じなら、同じ検証を通るので、復元した世界の完全検証は省きます。違えば、従来どおり復元した世界を完全検証します。Rustの拡張があるとき、EventLogの記録のbyte列は、追記のときに凍結された値からRustが書きます（Rustの規則の記録は最初からbyte列だけです）。すべての記録のbyte列をRustが書いたか確かめたログ（`EventLog.all_encoded`）は、復元してもそのログ自身になるので、復元の確認はそのログをそのまま読み、byte列の解析も比較もしません。Rustが書けない値（`str`の派生クラスなど）を持つ記録があるログと、Rustの拡張がないときのログは、次のとおりです。前の保存の確認で同じと分かった記録を比べ直さず、増えた記録だけを比べます。増えた記録は、保存したbyte列を読み、live の記録の各フィールドが、そのbyte列から復元する値と型まで同じかをRustで確かめます（`same_saved_records`）。復元した記録を作らずに同じことを確かめるためで、同じと言い切れないもの（`1`と`1.0`の違い、凍結されていない値など）は、従来どおり復元した記録を`==`で比べます。復元の確認で作る世界は比べたら捨てるので、保存した文書を写さずにそのまま使って組み立て、EventLogは前の保存の確認で作ったものに増えた記録だけを足して使います（索引もそのまま保ちます）。計算を再開したときと分岐したときは、読み込んだ（または分岐で作った）CheckpointのEventLogの文書と、そこから復元した記録を最初の保存で再利用します。復元した記録は、文書が記録と同じフィールドだけを持つとき、元の文書に戻るためです（`CheckpointHistoryCache.seed_events`）。復元の確認のKPIの標本も、前の確認で作った分を再利用して増えた分だけを読み、`model_state`の追記専用の履歴は、この保存で文書と等しいと確かめた項目を比べ直しません。分岐と再開では、活動中の行動を決める記録だけをRustのEventLogの索引から読むので（`active_action_index`）、記録を全件作りません。保存ごとのframeのケア履歴も、EventLogに持たせた前回の結果（`EventLog.derived`）に増えた記録だけを足します。
- 計算を進めるworkerの保存は、Rustの行が持つもの（人、設備、職員、支援の依頼、活動中のタスク、Rustが持つ名前空間と`metric_state`）を、Pythonのオブジェクトを読まずに行から正準JSONにします（`core/state_mirror.py`の`owned_row_bytes`、`EntityStore.rows_json`、`NamespaceMirror.row_json`）。byte列は`_canonical_data`のものと同じなので、hash、archiveのchunk、packは変わりません。実体のリストは文書の中で`SavedItems`です。行を持つものは`state_row!`と`OWNED_NAMESPACES`・`OWNED_FIELDS`の1行だけで、この経路に入ります。taintした行、丸ごと代入された項目、正準JSONが断る値（NaN）は、これまでどおりPythonのオブジェクトから作るので、エラーの文も同じです。hashの木が項目を分けて持つ名前空間（`_WORLD_TREE`）は、Rustが持ってもPythonの経路のままで（`body_state_v1`）、全体のbyte列も作りません。復元の確認の世界は、Rustの行を持たない素の世界です（`WorldState._bare_world`）。実体の行は、書かれていない限り同じbytesオブジェクトを返すので（行に書ける道はすべて印を付けます）、前の確認で等しいと示した行と同じオブジェクトなら、復元も比較もせず、前の確認のオブジェクトを使います。復元の結果は入力のbyte列だけで決まるからです。変わった行だけを今までどおり復元して比べます。Rustが持つ名前空間は、行のbyte列から読んだ文書を木と今までどおり比べます。`benchmarks/rule_shadow`で、保存のたびにPythonの経路のbyte列と、省かない比較の結果を比べています。
- 新しいchunkの秘匿情報の確認（`_reject_sensitive_checkpoint_content`）は、保存した1回分のchunkのbyte列をまとめてRustで読みます（`sensitive_candidates`）。Rustが返すのは、異なるキーのすべてと、パターンに一致しうる異なる文字列だけで、判定はPythonの同じ関数が行います。すでに保存したchunkは確認しません（それらは最初の保存で確認済みです）。byte列が1つでも違えば新しいchunkなので確認します。
- 計算を進める間（`TimelineStore`の継続計算）とCheckpointの読込の間は、Pythonの循環参照の回収（gc）の頻度を下げます（`core/collection.py`の`fewer_collections`、#234）。最も若い世代の回収を、新しいコンテナオブジェクト700個ごとから200,000個ごとにし、最後の区間が終わると元の閾値に戻します。閾値はプロセスに1つなので、区間が有効な間は同じプロセスのほかのスレッドにも効きます。Webサーバーでは計算が別プロセスで動くので、サーバーのプロセスに効くのはCheckpointの読込の区間だけです。1日分の計算（100人）ではCPU時間が約9%短くなり、ピークRSSが約47 MiB増えます。
- Webサーバー（`serve_inspector`）の`ProjectAPI`は、計算1回（`POST R/resume`）と分岐1回（`fork`、intervention-apply）ごとに別プロセスを起動して処理します（`web/worker_process.py`、`ProjectAPI(worker="process")`、#48）。起動はWindowsと同じspawn方式です。子プロセスがRunの書込権（`claim_run`）を自分で取り、取れたことをサーバーに知らせてから計算します。取れなければ従来どおり`run_worker_busy`で断ります。中止は`multiprocessing.Event`で伝え、サーバーのプロセスがなくなった場合も、子プロセスは次の保存境界で止まります。子プロセスが結果の状態を書かずに終わった場合（強制終了など）、サーバーはRunを`interrupted`にします。分岐の間はRunを`running`にし、サーバーが結果（`last_fork`）を記録してから元の状態に戻します。分岐の子プロセスが強制終了した場合も、Runは元の状態に戻ります。分岐の間も、サーバーはほかのHTTP要求に応えます。計算中もサーバーのプロセスはHTTPの応答でGILを取り合わず、計算が終わると子プロセスが使ったメモリはOSに戻ります。telemetryの`run_peak_memory_bytes`には、子プロセスのピークRSSを記録します。同じBranchの計算と、そのBranchからの分岐は1つずつですが、同じRunのほかのBranchや異なるRunは、上限（`sheltersim web --max-parallel-runs`、既定2）まで同時に、それぞれ別プロセスで計算・分岐します（#48）。書込権はBranchごとです。計算はそのBranchの、分岐は作る子Branchの書込権（`ProjectStore.claim_branch`、`branches/{branch}/worker-lock`）を取ります。Branchの書込権は、Runの入口のロック（`runs/{run}/worker-lock`）を一瞬だけ取ってから取ります。Runの削除・履歴索引の作り直し・回復のようなRun全体の操作（`claim_run`）は、入口のロックを持ち続けたうえで、どのBranchも書かれていないことを確かめます。占有ロックだけを使うので、Linux・macOS・Windowsで同じ組み方です。上限に達しているときの要求は、`background workers are busy` で断ります。計算1本で、1日分のRun（100人）なら約0.5〜0.9 GBのメモリを使うので、上限はCPUの数ではなくメモリに合わせて決めます。テスト、CLI、計測器（`benchmarks/investigate_performance.py`）は、同じプロセスのスレッドで計算します（`worker="thread"`、既定）。
- Branchの分岐（`TimelineStore.fork`）は、分岐する時刻の状態からCheckpointを1回だけ作ります。そのCheckpointが分岐の記録（`fork_origin`）の`state_hash`と`checkpoint_hash`になり、作成時の復元検証で組み立てた世界と指標が、そのまま子Branchになります（`Checkpoint.capture_restored`、#46）。この世界と指標は、Checkpointとも分岐元とも何も共有しません。子Branchに引き継ぐ応答テープは、分岐元のhead Checkpointの`runtime_state`だけを読みます。
- inspection、描画、metrics、trace levelはWorldStateを変えず、simulation乱数も消費しません。

ScenarioSpec、WorldState、Checkpoint、EffectProgram、Project recordはそれぞれ個別に版管理します。state変更には互換性テストが必要です。古い永続データを読み続ける場合は明示的な移行を用意します。

## 永続化とインターフェース

ProjectStoreとTimelineStoreは、ローカルProject、承認済みScenario、Run、Branch、Checkpoint chunk、asset、index付き証拠を保持します。CLI Run成果物にはmanifest、凍結Scenario、event記録、metrics、任意のモデル利用記録が含まれます。formatは有効化した機能によって異なります。APIリファレンスを参照してください。

HTTP APIは次の3領域を分けています。

- /api/v1/projects: 永続Projectと状態変更操作。
- /api/v1/runs: 保存Run成果物の上限付きread-only参照。
- /api/v1/demo: process内のデモBranch。

HTTPサーバーは既定で127.0.0.1にbindします。認証機能がないため、信頼できないネットワークへ公開してはいけません。

## 外部接続との境界

地域データProviderと任意Anthropic adapterはsimulation coreの外側にあります。Providerから得たデータは信頼せず、sourceと適用範囲を保持します。offline replayは保存済み応答か決定的fallbackを使い、過去時点の参照でlive Providerを呼びません。

モデル仮定と検証範囲はsimulation-models.mdとmodel-validation.mdを参照してください。
