# キャラクターと実移動のゲーム品質改善

`feature/ui-backup-20261025` の `d86ce15` から改修。シナリオ設定、承認、介入、
KPI、レポート、質問の既存機能を維持した。モデル係数・行動Policy・TickEngine・
保存Scenario/Run/Checkpointの形式は変更していない。有料LLMは呼んでいない。

## 不十分だった理由

1. RAFは動いていても、静止画面の呼吸モーションが中心だった。
2. `seat()` と物理位置の矩形変換を切り替えていたため、移動開始・到着で表示位置が飛んだ。
3. `sample()` は同一Zoneを中心に補間し、特に出発直後と部屋をまたぐ移動を落としていた。
4. 旧「60×」は60分先へ飛び、約700msで切り替える意味だった。実時間との比率ではなく、途中の移動も失われた。
5. 単独Timeline取得は各時刻をCheckpointから再構成するため、100人の先読みに追いつかない場合があった。
6. 小さな人型と人物に付いて動く敷物風プレートで、生活するキャラクターより固定アイコンに見えた。

## 描画

Canvas 2Dを維持し、**48×64px、8コマ、上下左右4方向**のローカルスプライトシートを
必要時に生成・キャッシュする方式へ変更した。毎フレームは主に`drawImage`を使う。
外部CDN、画像サービス、PixiJS/Phaserへの移行は不要。

頭・髪・顔・耳・襟・袖・靴・影を描き、服は無地・縞・前開きなどを使い分ける。
外見のバリエーションはIDから安定して決める演出で、人物属性から推測しない。
スタッフは青い制服・帽子・名札で識別する。待機者は服色を保ち、橙の小マーカーを表示する。
選択人物は足元リングとID・状態ラベルで強調する。ストレス等のレイヤーは記録値による色を使う。

歩行コマは**実際の表示上の移動距離**から決める。動かない位置で足踏みを歩行扱いしない。
向きは経路の局所的な接線から決め、曲がり角を通って4方向を切り替える。
停止中の人物には呼吸等の待機姿勢だけを使い、一時停止するとその姿勢も凍結する。
静的マップとスプライトを別々にキャッシュする。シートのキャッシュ上限は384。

## 記録から模式図への経路変換

物理経路の根拠には、同じedge、`active_journeys`の`route_points`、
`route_edge_ids`とGeometryのpolylineを使う。記録の始点・終点が経路上にあることを検証し、
必要な部分だけを切り出す。曲がり角を直線でショートカットしない。
Run・Branch・Geometryが異なる場合や、連続する1分境界でない場合には補間しない。

模式図では、各部屋の表示用出入口と周囲の通路へ、**根拠がある移動だけ**を変換する。
出入口は、記録された接続があるZoneに対応して表示する。部屋内・出入口・通路の各区間を
分け、他の部屋や壁を横切る直線は拒否する。模式図の距離は物理距離ではない。
元のID・所属・物理座標・経路参照を保持し、表示用座標をWorldStateへ戻さない。

待機列はAPIのqueue順序で配置する。到着途中の重なり回避は表示用の並べ方で、
待機順位とは区別する。従来の「動いている間は物理矩形変換、停止すると固定席へ戻る」
切替をやめ、連続する表示端点を経路で結ぶ。人物に敷物プレートを付けて移動させない。

経路が確定できない位置変化は歩行にせず、記録境界で状態を切り替える。
スタッフも、記録されたpositionとedge/運営経路がある場合だけ同じ方式で補間する。
今回の短期サンプルにはスタッフの物理位置変化がなく、架空の歩行を加えていない。
経路付きスタッフの補間は単体テストで検証した。

## 再生時計とバッファ

- 1×＝実時間1分でシミュレーション1分。既定の60×＝実時間1秒でシミュレーション1分。
- 1/5/15/60/120/240×を選択でき、倍率変更時も現在の端数時刻から続ける。
- 時計は`performance.now()`の経過時間で進み、フレーム数には依存しない。
- 1分刻みを保って最大8境界ずつ先読みし、クライアントの保持数は概ね最大17フレーム。
- 未取得の境界へは進めず、読込待ちは「時刻を保持」と表示する。取得後に遅延分を一気に追いつかせない。
- A/Bは同じ時計・区間・補間率を使い、片側だけ進めない。
- 一時停止は位置・姿勢・時計を凍結。再開は同じ端数から続く。
- シーク・Run/Branch・ページ切替で古いバッファと描画世代を破棄し、遅れた応答を無効化する。
- 画面非表示では一時停止。`prefers-reduced-motion`では装飾モーションを抑える。

## 区間取得APIと保存境界

`GET R/replay-frames?branch_ids=A,B&start=M&end=N` を追加した。
1〜2 Branch、両端を含む最大8個の計算済み境界に限定する。
1 Branchなら既存Timeline frame、2 Branchなら既存比較と同じ形式の`samples`を返す。
比較のKPI差分はサーバーの共通projectionを使い、フロントで作り直していない。

既存`TimelineStore.iter_worlds`で順次復元し、次のtickへ進む前にprojectionをdeep copyする。
未計算・fork前・過大範囲・重複Branch・読み取り中のhead変更は拒否する。
保存Branchを進めず、record Runでも記録済みProvider応答だけを使う。

既存record Runとの照合で、時刻0だけstate hashが異なるケースを検出した。
連続読取りヘルパーが最初の観測より先にcontrollerを初期化していたため、
最初の境界をyieldしてから次tickの準備をする順序へ修正した。
単一Checkpointの読取りではcontrollerを作らない。計算規則・保存済みstateは変更しない。
record Runの0〜3分が単独取得と完全一致し、LLM利用状態も変わらないことを確認した。

## 人数と実移動の計測

同じ実Runの0〜12分、12組の連続境界で比較した。人数は重複除外、
「区間数」は1 Agent×1分境界の組数であり、独立した移動イベント数ではない。

| 指標 | 30人Run | 100人Run |
|---|---:|---:|
| 期間内に移動状態になったAgent | 18人 | 45人 |
| Zoneが変わったAgent | 18人 | 45人 |
| 経路記録があるAgent | 18人 | 45人 |
| 表示補間できたAgent | 18人 | 45人 |
| 改修前の表示移動区間数 | 22 | 39 |
| 改修後の表示移動区間数 | 74 | 192 |
| 経路不明などで状態切替した区間数 | 23 | 31 |
| 状態切替を含むAgent | 14人 | 25人 |
| スタッフの物理位置変化 | 0 | 0 |

状態切替と補間の人数は重複する。位置変化のうち、経路が残っていない待機列の
再配置等を無理に歩行へ変換していない。

実Chromeの7枚の連続フレームでは、30人Runの15人、100人Runの37人について、
3px超の画面上の移動と歩行コマの変化を**同じ人物IDで**確認した。
RAFや呼吸だけが動くケースを合格扱いしない。
区間APIで再生した画面座標を、独立した単独Timeline取得から再計算した座標と比較し、
最大誤差は浮動小数点の丸め程度（約`6e-14px`）だった。

## 性能と3画面

1440×900、device scale factor 1、実Chrome headless。録画・スクリーンショット処理を
性能測定の区間から外し、実際に時計と人物位置が進む区間で測定した。

| 場面 | FPS | 平均描画時間 |
|---|---:|---:|
| 30人シミュレーション | 約60 | 約0.59ms |
| 30人×2の比較 | 約60 | 約0.63ms |
| 100人シミュレーション | 約60 | 約0.51ms |
| 100人×2の比較 | 約60 | 約0.68ms |

100人時のChromeページTaskDuration/経過時間は約8.8%。端末全体やPython側の
過去記録復元のCPU時間ではない。場面の異なる局所計測で、全端末・長期Runの保証ではない。
倍率の実測は100人時で1×が約1.00倍、120×が約119.6倍。純粋な時計テストでは
60×で実時間1000ms＝シミュレーション1分を厳密に確認する。

- シミュレーション：個別スプライト、歩行、待機、レイヤー、人物選択。
- 比較：両マップの座標移動・時計・倍率・視点を同期。停止後の両画像も不変。
- レポート：同じスプライトとマップを静止表示。最終状態に架空の歩行を付けない。
