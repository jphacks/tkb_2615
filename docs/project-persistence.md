# Projectの永続化、正確な時刻、復旧

Web serverはRUNS_DIR/.projectsを開き、ProjectAPI経由で/api/v1/projectsを提供します。Scenario版とRun入力は不変です。条件編集では新しいScenario版を保存してからRunを作ります。Branch位置は、integrity確認済みCheckpointの保存後にだけ進めます。browser再読込後も同じIDを参照できます。server再起動時は中断済み作業として記録し、最後に完了したCheckpointから再開します。不完全なchunkを完了扱いしません。

同じ操作をCLIから利用できます。

~~~text
sheltersim project --root runs/.projects create --project-id study
sheltersim project --root runs/.projects save-scenario --project-id study --scenario scenario.json --approved-hash <reviewed-canonical-sha256>
sheltersim project --root runs/.projects new-run --project-id study --run-id trial --scenario-id <id> --scenario-version 1
sheltersim project --root runs/.projects resume --project-id study --run-id trial --minute 100
sheltersim project --root runs/.projects frame --project-id study --run-id trial --minute 73
sheltersim project --root runs/.projects fork --project-id study --run-id trial --minute 73 --child-id alternative
~~~

approved hashは確認した正準ScenarioSpecそのものに結び付きます。Webの計算開始（POST R/resume）は、BranchのポインタとScenarioの期間だけで目標時刻を検査して受け付けます。head Checkpointの展開と検証はworkerが1回だけ行い、破損や非互換を検出した場合はRunを `failed` にして、Branchのポインタは変えません。CLIとWebの継続実行は設定されたLLM modeを使い、モデル設定と費用記録を保持できます。過去frameの読み出しではnetwork adapterを作りません。offline履歴が暗黙にlive履歴へ変わることはありません。記録が欠落または非互換なら、過去の再構築を拒否します。

時刻Mはtick Mの直前境界です。timelineのWorldState KPIはその境界で取得します。保存metrics.csvはtick終了時刻の意味を保ちます。frameにはexact、state_hash、computed_untilを含み、未計算時刻は拒否します。親と兄弟のstateは独立しています。geometry点を物理メートルとして扱うのは検証済みmovement位置がある場合だけです。旧来の表示用位置はdisplay_onlyと表示します。

Checkpointは `runs/{run}/checkpoints/` に、目録（manifest、`{checkpoint_hash}.json`）とgzip圧縮したchunkで保存します。chunkは正準JSONのSHA-256を名前に持ち、同じ内容は一度だけ書きます。目録の `checkpoint_archive_v3` では、1回の保存で新しく増えたchunkを1つのpackファイル（`checkpoints/packs/{packのSHA-256}.pack`）にまとめて書き、目録の `locations` に、各chunkがどのpackの何byte目から何byteかを記録します。前の保存のpackにあるchunkは書き直さず、その場所を参照します。目録のhash（`manifest_hash`）は `locations` も含み、読むときは今までどおりchunkごとに名前のSHA-256と照合します。これより前の `checkpoint_archive_v1`・`v2` の目録は、chunkを1つずつのファイル（`checkpoints/chunks/{SHA-256}.json.gz`）に置いていて、そのまま読めます。v2のRunを続けて計算すると、既存のchunkファイルを参照し、増えた分だけをpackに書きます。Checkpointの内容とhashは、置き方によらず同じです。v3の目録は、v3に対応する前の版のコードでは「unsupported checkpoint archive version」として読めません。保存1回で書くファイルとfsyncはpack1つ分になり、容量の計測で数えるファイルも、保存の回数程度に収まります。

Checkpoint v2のhash（`state_hash`・`checkpoint_hash`）は、文書全体のSHA-256ではなく、chunkのhashの木の根です。`event_log`、`model_state`の追記専用の履歴（`body_state_v1.history`、`shared_operations_v1.history`、`resource_ledger_v1.audit`、`resource_service_v1.request_history`・`queue_stall_history`）、`metrics_state`の`snapshots`・`resource_snapshots`は、128項目ごとの正準JSONのSHA-256（archiveのchunkの名前と同じ）と項目数からhashを作ります。そのほかの値は正準JSONのSHA-256で、これらを含むobjectはフィールドごとのhashからhashを作ります。保存は新しいchunkだけをhashします。決まりは文書だけで決まるので、archiveのどの版からでも、単独のJSONからでも同じ値になります。`schema_version`が1のCheckpointは、従来どおり文書全体のSHA-256で確かめて読み、再生・分岐・比較に使えます。v1の先頭から計算を続けると、それ以降の保存はv2になります（v1の版のコードではv2を読めません）。計算の結果を比べるhash（`benchmarks/investigate_performance.py`のworld・events・KPI、CLIの`final_state_hash`）は正準JSON全体のSHA-256のままです。Inspectorの`state_hash`の表示は、Checkpointの持つ値なので、v1の時刻とv2の時刻で決まりが異なります。

Checkpointを保存したworkerは、その時点のframeをメモリ上のWorldStateから描画し、`runs/{run}/frames/{checkpoint_hash}.json.gz` に保存します。frameはCheckpointから導出できる置き換え可能なread modelで、`schema_version: 1`、描画版 `timeline-frame-v1`、元の `checkpoint_hash`、frame本体のSHA-256を持ちます。timeline GETは、要求時刻が保存境界で、キャッシュの版・hash・Run・Branch・時刻が一致する場合だけそのframeを返し、`computed_until` を現在のBranch値に置き換えます。それ以外の時刻、旧Run、欠落・破損・版不一致のキャッシュは従来どおりCheckpointから復元して描画します。GETはキャッシュを書き込みません。キャッシュの書込失敗や容量超過はCheckpoint保存を失敗させず、次の読取が復元経路になるだけです。描画結果を変える変更では `FRAME_PROJECTION_VERSION` を上げます。

Runの計算の状態（queued、running、paused、completed、failed、interrupted）は、Branchごとに `runs/{run}/branches/{branch}/status.json`（`schema_version: 1`）に記録します（#48）。Runの `status.json` の `status` は、どれかのBranchが計算中ならrunning、そうでなければ最後に止まったBranchの状態（分岐の後は分岐の前の状態）を要約として持ちます。Runの参照（`GET …/runs/{run}`）の `branches` の各要素には、記録があればそのBranchの `status` が付きます。この記録より前に計算したBranchには `status` がありません。分岐の途中でプロセスが終わり、子Branchが作られなかった場合は、子の状態の記録を消します。サーバーの起動時の回復は、計算中のまま書込権を持つプロセスがいないBranchを `interrupted` にします。archiveは記録を保持するだけで、disk容量を空けません。deleteは非稼働Runに対し、同じRun IDを明示確認した場合だけ実行でき、そのRunだけを削除します。ProjectStoreは容量とfile数を返します。容量は呼ばれるたびにdisk上の通常fileを数え直すので、ほかのprocessが書いたfileも含みます。ただしCheckpointの保存1回の中では、最初に1回だけ数え、それ以降はその値に、その保存が書いたbyte数とfile数を足して使います。保存の途中でほかのprocessが書いたfileは、次に数え直すときから数えます。そのprocessは書く前に自分で数え直すので、容量上限を超えるのは、その保存が書く分までです（#237）。symlinkは数えず、たどりません。数えている間に消えたfile（書込途中の一時fileなど）は0 bytesとします。容量上限を超える書込は、保存fileでも履歴索引でも拒否し、書く前の状態に戻します（#47）。Checkpointは版管理されたgzip chunkとcontent hashを使い、公開Checkpoint JSON v1と従来のraw保存も読み込みます。Scenario、Run、Branch IDは実在避難者名ではなく安定識別子です。credential fieldを拒否し、一般的なsecret/contact文字列をredactまたは拒否します。メールアドレスは、`@`のあとのドメインの末尾が英字などの文字のものだけを検出します（`storage/projects.py`の`EMAIL_ADDRESS`。Run成果物と保存Runの表示も同じ定義を使う）。モデルの署名のように`@`のあとに小数点を含む値は、連絡先とみなしません（#187）。電話番号は、区切りのある3つの数字の組（`090-1234-5678`、`+81 90 1234 5678`など）を検出します（`PHONE_NUMBER`。Run成果物と保存Runの表示も同じ定義を使う）。論文のDOIや日付は電話番号とみなしません。区切りのない数字の並びは検出しません（#190）。Checkpoint保存時のこの検査は、archiveがまだ保存していないchunkの値と、分割されたobjectのフィールド名に対して行います。既存chunkは最初の書込時に同じ検査を通っています。新しいchunkは全検査が通ってから書き込むため、拒否されたCheckpointは何も書きません。workerが `capture()` した直後のCheckpointは `save_captured_branch` で保存し、`capture()` 時の検証を再実行しません。このときarchiveは、`capture()` が再利用した履歴の正準JSON byte列からchunkを作り、分割の判断に使う大きさも同じbyte列から求めます（#44）。それ以外の入力は `save_branch` が再検証します。保存済みCheckpointの読込は、展開した文書をコピーせずに検証し、その検証で復元した世界と指標を、計算の続き（`advance`）や途中時刻の再計算（`seek`）でそのまま使います（`load_restored_checkpoint`、#46）。ProjectStoreは、最後に読み込んだ2つのCheckpointについて、復元した世界と指標の手つかずの複製をcheckpoint hashごとに持ちます（比較と再生は2本のBranchを読むため）。同じCheckpointをもう一度読むときも、文書の展開とmanifest・chunk・`checkpoint_hash`・`state_hash`の確認は毎回行い、復元の代わりに持っている複製のコピーを返します。Checkpointの文書は内容のhashで名前が決まり変わらないので、同じhashの文書から復元した状態は同じです。コピーでは、変更されないEventLogの記録と予定イベントを共有します。持ち続ける世界の分だけ、Webサーバーのプロセスのメモリが増えます（#245）。複製はEventLogの記録を元の世界と共有するので、持っている間はその記録も残ります（1440分の世界1つで、Pythonのメモリ約140 MiB）。読み終わったあとまでメモリを占めないよう、どの複製も最後の読込から60秒使われなければ捨て、循環参照の回収を1回行います。計算を進めるときの読込（`advance`）では複製を作りません。先頭のCheckpointは計算が保存するたびに新しくなり、読み直されることがほとんどないためです。会話記録はserverが検証したRun/Branch/時刻に結び付くEvidenceReferenceを使い、browserから送られたkeyを保存しません。

Runの履歴（`history`）は、計算しながら書く履歴索引（`runs/{run}/history.sqlite`）から読みます。索引には、Checkpointから作れる記録（イベント、KPI、社会・職員・人口の履歴など）のほかに、計算中に記録した行動・会話の判断（候補、方針の版など）が入ります。判断はCheckpointに入らないので、索引を作り直すと戻りません。そのため「既存Runの履歴索引を再構築」（`POST R/index`）は、索引が分岐の先頭のCheckpointと一致しているとき（状態`ready`）は`history_index_current`で断ります。作り直せるのは、索引のない古いRunや、先頭がずれた索引だけです。作り直した索引には判断の記録がなく、応答の`limits`にそのことを書きます（#213）。索引への登録はCheckpointの保存1回ごとに1つのトランザクションで行い、記録を数百件ずつまとめて書き込みます。索引はSQLiteの従来のジャーナル方式で書きます。WAL方式（#268）は、すべてのページをログと本体に2回書くため、1日分の登録のcommitが約2倍かかり、WSLでは時々10〜15秒長くなったので戻しました（#269）。WAL方式のときに書いた索引は、次の書込みで従来の方式に戻ります（ほかの接続が開いている間は、その次の書込みで戻ります）。すでにある記録と同じkeyの記録は追加せず、内容が違えば`immutable_history_record_conflict`で拒否して、その登録全体を戻します（#47）。保存はBranchのポインタを新しいheadに書き換えてから索引に登録するので、その間の読取りでは、索引がポインタより後れています。保存が8回以上ある長い計算では、索引への登録を別のプロセスで計算と並行して行います（`storage/index_writer.py`、`BackgroundIndexer`）。計算側は保存のたびに、前の保存から増えたEventLogの記録とKPI・資源の標本、登録が読む時刻以後の履歴の項目、model_stateの名前と設定だけを送り、登録のプロセスが保存の順に1つずつ登録します。送った分の先頭が索引の記録している位置と合わなければ、`history_index_out_of_step`で断り、計算を失敗にします。登録が2回分より遅れると計算側が待ち、計算の終わりには登録が追いつくのを待ってから状態を`paused`・`completed`にします。そのため計算中の索引は、ポインタより最大で保存2回分後れます。計算のプロセスが途中で止まると、まだ登録していない保存のCheckpointは索引の一覧（`checkpoints`）に載りません。次の計算は索引の記録している位置から登録を続けるので、記録は欠けませんが、その時刻の過去の参照は、一覧にある前のCheckpointから計算し直します。この間も、frame・比較・再生は索引のheadまでのCheckpointと新しいheadで答え（#259）、履歴（`history`）・Checkpointの一覧・会話記録は索引のheadの時点で答えます（#262）。履歴とCheckpointの一覧の応答の`anchor_hash`と`indexed_through_minute`は、答えに使った索引のheadとその時刻です。履歴の検索は1つの読取りの中で索引のheadの時点に揃うので、検索の途中でポインタが動いても`history_changed_during_query`で断りません。ページ送りのcursorはそのheadに結び付き、headが変わると従来どおり`stale_or_foreign_cursor`になります。索引がポインタより先にある場合や、Branchの行がない場合は、従来どおり`history_index_stale`です。分岐した子Branchは、分岐元の行を写さず、分岐の時刻より前の行は分岐元の索引から読みます（#256）。索引の`lineage`表に、子Branchごとに分岐元と分岐の時刻を記録し、履歴の検索は「その Branch の行」と「分岐元の、分岐の時刻より前の行」（分岐元がさらに分岐していれば、その分岐元の、小さい方の分岐の時刻より前の行）をあわせて読みます。会話記録は Branch ごとのもので、分岐元のものは読みません。子Branchが登録するのは分岐の時刻以後の行だけで、分岐元が分岐の時刻より前に持っている行と同じkeyの行は登録しません（内容が違えば`immutable_history_record_conflict`）。そのため分岐は、索引の行を写す時間も、そのぶんの容量も使いません。子Branchは、分岐元が計算中に記録した、分岐の時刻より前の行動・会話の判断も読めます（Checkpointから作れないため、以前は子Branchにありませんでした）。作り直し（`POST R/index`）をしたBranchは、すべての行を自分で作り、分岐元を読まなくなります。`lineage`表を持つ索引は版2（`PRAGMA user_version=2`）で、版2を知らない前のコードは`history_index_version_unsupported`で読み書きを断ります。版1の索引は、そのまま読め、次の書込みで版2になります。版1のときに分岐した子Branchは、写した行を持ち、`lineage`の行がないので、従来どおり自分の行だけを読みます。

no-op childは親に記録された既存Provider応答を、cache/fallback/費用metadataごと引き継いで再生します。明示的に通常継続を依頼した場合は設定済みrouterで記録範囲の先へ進められますが、過去seekがProviderへfallbackすることはありません。承認済み介入は将来分の継承response replayを無効にし、既に発生した予算記録と過去の承認済みtapeは保持します。
