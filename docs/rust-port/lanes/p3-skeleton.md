# P3：Rust の骨組みと、境界の費用の計測

設計の P3 と、P4 の前に済ませる計測の記録です。計測はすべて他の重い処理と同時に動かした回で、値は範囲で示します（WSL2、16コア、Python 3.12.3、PyO3 0.23 abi3-py312、LTO）。負荷が低い回と高い回（load average 約10〜70）で数倍違います。

## 結論

| 止める基準 | 結果 |
|---|---|
| 転送する書き込みが 3 µs を超える | **1項目の書き込みは下回る**（0.12〜1.3 µs）。**記録を丸ごと入れる書き込みは負荷しだい**（2.2〜8.2 µs）。**名前空間ごとの置き換えは大きく超える**（資源台帳で約 60 ms） |
| tick が 25% を超えて遅くなる | **今の設計のまま全部を写すと超える**（+33〜36%）。名前空間ごとの置き換え4つを転送しなければ +18%（+7〜33%）で、窓口の見積もりを足して約 +21% |

## 実際の tick での比較

Python で書いた追跡する dict・list で `model_state` の19の名前空間をすべて包み、すべての書き込みを Rust の `V` の木へ転送しました。Rust の確認は派生型も受け入れるように変えた複製で、`domain/body_state.py:805` の別名も直しました。同時に動かして負荷をそろえ、スレッドの CPU 時間を比べました。240 tick、4回です。

| 条件 | 基準との比（中央値、範囲） |
|---|---:|
| 同じ基準をもう1つ（ばらつきの確認） | 1.00（0.94〜1.02） |
| 資源台帳を写さない | 1.36（1.25〜1.46） |
| 資源台帳は新しい項目だけを送る | 1.33（1.21〜1.42） |
| 名前空間ごとの置き換えをする4つを写さない | 1.18（1.07〜1.33） |

全部をそのまま転送した回は、順に動かした4回で基準の 1.7〜4.9倍の壁時計時間でした。この条件だけ同時には動かしていません。

どの条件でも、最後の世界のハッシュは基準と一致しました（120 tick と 240 tick）。この区間に「写して差し替える」処理は起きていないので、その経路はこの比較で確かめていません。Rust 側の `V` の木と写しの一致も比べていません。

## 設計への提案

1. **名前空間の置き換えを転送の対象にしない：** `world.model_state[ns] = ...` を書くコードは、その名前空間を Rust に移す作業と同じ変更で移します。資源台帳は `apply_resource_operation` と一緒に、心理は `update_long_term` と `runner.py:661` と一緒に移します。P5 のひな形は、今の心理の置き換えを残さないようにします。
2. **写すのは持ち主を移した名前空間だけ、を tick の予算で守る：** 上の +18% は全部を同時に写した最悪の場合です。実際には名前空間ごとに写し、規則も一緒に移ると転送は消えます。作業ごとに同時実行の比較を取り、印ごとに 25% を確かめます。
3. **窓口は借用確認つきで始める：** 借用確認の費用は1回 5〜10 ns ほどで、`frozen` と `UnsafeCell` にする理由にはなりません。
4. **dict の派生型は abi3 でも C で作れる：** 設計の「abi3 では dict を派生できない」は PyO3 の `extends` の話で、PEP 697（負の `basicsize`、`PyObject_GetTypeData`）を使えば Python 3.12 の安定 ABI で `mp_ass_subscript` を Rust で書けます。転送は 21〜168 ns で、Python の上書きより約5倍速くなります。Linux の Python 3.12 だけで確かめました。P4 で転送の費用が予算を圧迫するなら、この形にします。

## 骨組み

- `native/build.rs`：`src/state/*.rs`・`src/rules/*.rs` を見つけ、モジュールと Python のサブモジュールにします。ファイルを足すだけで `lib.rs` も `sheltersim/native.py` も変えずに使えることを、一時ファイルで確かめました（Linux のみ。Windows・macOS は CI で確かめます）。
- `native/src/core/`：`value.rs`、`mathx.rs`、`rng.rs`、`interner.rs`。使い方は `native/README.md` にあります。
- `native/clippy.toml`：16項目を禁止しました。そのうち12種類の呼び出しがエラーになることを、一時ファイルで確かめました（`swap_remove_entry` などの4項目は呼んでいません）。今のコードに違反はありません。
- `psychology.rs` の `exp`・`expm1` と `contacts.rs` の抽選は `core` を使います。`math.exp` が例外を出す値では、Rust は値を返さず `Unsupported` になり、Python が判定します。

## CPython との一致（`tests/integration/test_native_parity.py`）

標準の実行は約5秒です。`SHELTERSIM_PARITY_CASES=2000000` でも全項目が一致しました。CPython と違う値はありません。ただし次の値は `None` を返して Python に任せます。

- `pow` の結果が非正規化数のとき：glibc が `ERANGE` を立てることがあり、CPython はそのとき `OverflowError` を出します。
- `round` の負の桁数：今の規則では使っていません。
- `sum_nums` で整数が i64 を超えるとき、`fsum` で途中の和が有限でなくなるとき。

`**` については、次のことを確かめました（100万個の値、glibc）。

| 書き方 | 機械語 | `x ** 2`・`x ** 0.5` との違い |
|---|---|---:|
| `x.powf(2.0)` | `mulsd` | 790個 |
| `extern "C"` の `pow(x, 2.0)` | `mulsd` と同じ | 790個 |
| `x.powf(0.5)` | `sqrtsd` | 865個 |
| `extern "C"` の `pow(x, 0.5)` | `pow` の呼び出し | 0個 |
| `pow(black_box(x), black_box(2.0))` | `pow` の呼び出し | 0個 |

定数の引数の `exp(1.5)` もコンパイル時に計算されるので、`mathx` はすべての引数を `black_box` に通します。

## CI への提案（このレーンでは変えていません）

Linux の job で `cargo clippy --manifest-path native/Cargo.toml -- -A clippy::all -D clippy::disallowed_methods` を実行します。`clippy.toml` は実行しなければ効かないので、入れることを勧めます。他の lint は既存のコードに残っているので、禁止だけを対象にします。3つの OS の一致は、既存の CI が `test_native_parity.py` を動かすことで確かめられます。
